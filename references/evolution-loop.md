# 演进循环（Evolution Loop）

目标：不是“跑完一轮就结束”，而是让测试沿着**结果驱动的方向**持续加压：每一代都基于上一代的观测，选择边界、压力、并发、长稳、故障或差分方向，记录前沿（frontier），直到预算/风险/收益停止。

## 1. 循环骨架

```text
        ┌─────────────────────────────────────────────┐
        │  0. 载入状态：frontier / signals / budget     │
        └──────────────────────┬──────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────┐
        │  1. 观察：最新结果 + 证据 + 性能/资源/失败     │
        └──────────────────────┬──────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────┐
        │  2. 决策：继续/升级/收敛/最小化/停止           │
        └──────────────────────┬──────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────┐
        │  3. 生成下一代：一次一个主轴 + 可选一个副轴    │
        └──────────────────────┬──────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────┐
        │  4. 执行：资源锁 / 并行 / 独占 / 超时          │
        └──────────────────────┬──────────────────────┘
                               ▼
        ┌─────────────────────────────────────────────┐
        │  5. 记录：case/结果/证据/lineage/next          │
        └──────────────────────┬──────────────────────┘
                               ▼
                    预算/停止条件满足？──是──► 停止并写 loop-report
                               │否
                               └──────────────► 回到 1
```

## 2. 状态文件

`<run>/09-loop/`：

| 文件 | 作用 |
|---|---|
| `state.json` | 当前代、预算、前沿、信号、观测、下一代建议、停止原因 |
| `iterations.jsonl` | 每代一行：case、outcome、metrics、变更轴、证据、next |
| `frontier.md` | 人读前沿：当前最大负载/并发/时长/最小 buffer/最高开销 |
| `loop-report.md` | 循环总结：走了哪些方向、为什么停、下一轮种子 |

最小状态：

```json
{
  "iteration": 1,
  "budget": {"max_iterations": 10, "max_wall_sec": 7200},
  "frontier": {"max_kernel": 5000, "max_threads": 4, "max_soak_sec": 120, "min_buffer_bytes": 8192},
  "signals": {"failures": [], "drops": 0, "max_overhead_pct": 62.0, "rss_growth_kb": 608000},
  "next": [{"axis": "concurrency", "why": "...", "params": {"threads": 8}}],
  "stop": false,
  "stop_reason": ""
}
```

## 3. 观察什么

每代至少读取：

- 结果状态：PASS / FAIL / TIMEOUT / SIGNAL / ENV_BLOCKED / INCONCLUSIVE。
- 数据对账：生产量、消费量、dropped、重复、计数差异。
- 稳定性：宿主输出/退出码/信号/挂起。
- 性能：off/on、P50/P95/P99、CPU、吞吐、开销百分比、方差。
- 资源：RSS、线程、fd、日志量、临时文件、句柄。
- 环境：设备/版本/权限/并行干扰。
- 失败模式：crash/abort、死锁、丢数、错误码、慢、资源涨。

没有量化信号时，不允许“感觉再压一点”；要么补观测，要么明确“探索性”。

## 4. 决策表

| 观测 | 决策 | 下一代 |
|---|---|---|
| 有未最小化的 FAIL | 收敛 | 最小复现；二分参数/序列；固定 seed |
| dropped > 0 | 找阈值 | 减半 buffer、×2 负载、增加消费者延迟；记录丢数曲线 |
| host_ok=false / crash / hang | 稳定性优先 | 降载隔离；单线程/单 kind；加 timeout/进程组；再回归 |
| 开销 > 预算/基线 | 归因 | 按 kind 拆分；降 flush 频率；对比 off/on；换真实负载 |
| 资源持续增长 | 长稳 | ×2 duration；周期采样；对照关闭组件的基线 |
| 全部 PASS 且前沿未到上限 | 升级 | load ×10、threads +4、buffer ÷2、soak ×2、组合维度 |
| 连续 2–3 代无新信号 | 换轴 | 从功能/边界转到故障/ABI/差分/多进程 |
| 预算耗尽/风险上限 | 停止 | 写 loop-report + 下一轮种子 |

“升级”不是一次把所有参数拉满；一次只改一个主轴，记录变更因子。

## 5. 变异算子

| 轴 | 算子 | 典型因子 | 观察 |
|---|---|---|---|
| 负载 | iterations ×10 | 5k→50k→500k | 丢数/延迟/资源拐点 |
| 并发 | threads +4 / ×2 | 4→8→16 | 竞态/死锁/计数 |
| 压力 | buffer ÷2 / 消费者延迟 ×10 | 8MB→4MB→2MB→4KB | dropped/背压/线程峰值 |
| 长稳 | duration ×2 | 120s→300s→600s→1h | RSS/fd/线程/吞吐漂移 |
| 生命周期 | cycles ×2 | 20→50→100 | 线程/fd/句柄/重初始化 |
| 故障 | 注入组合 | 无 preload + 慢消费者 + 并发 finalize | 宿主连续性/降级 |
| 边界 | 0/1/MAX/空/超长/短缓冲 | 0、1、SIZE_MAX、UINT32_MAX | 错误码/崩溃 |
| 组合 | 主轴 + 副轴 | 高压 + 8 线程 | 交互故障 |
| 差分 | 开/关、旧/新、参考实现 | A/B | 行为/性能差异 |

每个 case 必须写 `lineage`：`new`、`reuse:<case>`、`evolve:<case>`，并写清“相对上一代改了什么、因子是多少”。

## 6. 预算与停止

预算至少包含：

- 最大代数（默认 10）。
- 最大墙钟（默认 2h）。
- 单代最大 case 数/最大时长。
- 设备/端口/许可资源。
- 风险上限：不允许破坏性操作；性能/长稳必须独占。

停止条件（任一）：

1. 预算耗尽。
2. 连续 3 代无新信号（前沿不变、无新失败、无新拐点）。
3. 达到风险/资源上限。
4. 目标不变量已被充分证明，继续加压收益低。
5. 环境阻塞且无法恢复。

停止时必须写：走过哪些轴、当前前沿、未覆盖、下一轮建议。

## 7. 记录与前沿

每代 `iterations.jsonl` 一行：

```json
{"iteration":2,"case":"C-026","axis":"concurrency","change":"threads 4->8","outcome":"pass",
 "metrics":{"kernel":32000,"dropped":0},"evidence":"05-evidence/C-026/attempt-1/result.json",
 "next":["soak 120->300s"]}
```

前沿 `frontier.md`：

| 轴 | 当前前沿 | 证据 | 下一目标 |
|---|---|---|---|
| load | 5,000 kernels | C-08 | 50,000 |
| concurrency | 4 threads | C-11 | 8 |
| pressure | 8KB buffer | C-09 | 4KB |
| soak | 120s | C-23b | 300s |
| overhead | 62–75% | C-23a | 按 kind 归因 |

通过的高压点成为新 baseline；失败点成为 regression；不要每代重复同一个点。

## 8. 反模式

- 每代随机换多个参数，无法归因。
- 只重复“已经通过”的负载，前沿不前进。
- 把 flaky 当新发现，不固定 seed/不复现。
- 为了“有进展”把环境问题写成产品缺陷。
- 性能/长稳与其他负载共享设备后下结论。
- 不做 off 基线，把宿主缓存增长当库泄漏。
- 预算无上限，跑到资源/设备异常。

## 9. 与 runner 的配合

```bash
python3 <skill>/scripts/evolve.py init --run-dir <run> [--known-failures C-04]
python3 <skill>/scripts/evolve.py next --run-dir <run>
python3 <skill>/scripts/evolve.py record --run-dir <run> --case C-026
python3 <skill>/scripts/evolve.py status --run-dir <run>
```

`record` 会读取该 case 的最新证据，更新前沿/信号，并重算下一代建议；`next` 不执行测试，只给出方向与参数。
